# 리뷰어 지시문

`pr-review-cycle` 3 단계(첫 리뷰)와 5 단계(재리뷰)에서 리뷰어 서브에이전트에게 보내는 지시문이다. `<...>` 를
채워 보낸다. 리뷰어는 이 대화를 모르므로 필요한 것은 지시문과 아래 "리뷰어 규칙" 절에 모두 있어야 한다. 내 판단이나
예상 문제는 넣지 않는다.

## 첫 리뷰

```text
PR #<PR> 를 리뷰해 PR 에 리뷰를 올리고, 짧은 알림만 돌려주세요. 당신의 이름은 pr-<PR>-reviewer 입니다.

- 저장소: jay-park-lab/hmgapi-nx4-kor (github.com). base <base 브랜치>, head <브랜치> (<head SHA>)
- 브랜치 종류: <feature | release | hotfix>
- PR: <PR URL>
- 로컬 체크아웃: <체크아웃 절대 경로>. 읽기만 하고 파일은 바꾸지 마세요.
- 개인 설정 파일: <체크아웃 절대 경로>/.env.local. 시험에 쓸 경로(HMGAPI_SRC 등)가 있습니다. 내용을 출력하지 마세요.
- 저장소 규칙: CLAUDE.md, docs/git-flow.md, docs/design.md

리뷰 방법은 <체크아웃 절대 경로>/.claude/skills/pr-review-cycle/references/reviewer-brief.md 의
"리뷰어 규칙" 절을 읽고 그대로 따라 주세요.
```

## 재리뷰

```text
PR #<PR> 재리뷰 요청(<N>차): 지난 리뷰의 <지적 번호들> 을 반영한 커밋을 봐 주세요.
PR 에 리뷰를 올린 뒤 짧은 알림만 돌려주세요.

- 범위: <지난번에 본 커밋>..<새 head SHA>, 그리고 고친 PR 본문
- 지난 리뷰: <자동 리뷰 링크 목록>. 이 PR 을 처음 보는 리뷰어라면 먼저 읽어 주세요.
- 새 지적 번호: <지금까지 쓴 가장 큰 번호 + 1> 부터
- 반영 답글: <답글·코멘트 링크 목록>
- 반영 요지:
  - <지적 번호>: <무엇을 어떻게 고쳤는지, 어떻게 확인했는지 한두 줄>
  - <반영하지 않은 지적 번호>: <이유와 후속 처리>
- 봐 주실 점:
  1. 지난 지적이 해소됐는지(해소 / 일부 / 미해소)
  2. 고친 내용이 실제로 동작하는지(직접 재현)
  3. 새로 생긴 문제
  4. CI 결과(없으면 없다고)
- 리뷰어 규칙이 지난번 뒤 바뀐 것: <바뀐 절과 요지, 없으면 "없음">

리뷰 방법은 <체크아웃 절대 경로>/.claude/skills/pr-review-cycle/references/reviewer-brief.md 의
"리뷰어 규칙" 절을 이번에도 처음부터 다시 읽고 따라 주세요. 기억에 기대지 마세요.
```

## 리뷰어 규칙

### 언어

리뷰 본문, 인라인 코멘트, 답글, 돌려주는 알림은 모두 존댓말 한국어로 쓴다. 코드, 명령, 파일 경로, 식별자는 그대로 둔다.

### 도구

GitHub 작업은 `gh` 와 `gh api` 로 한다(github.com). 아래 `<R>` 은 `jay-park-lab/hmgapi-nx4-kor` 다.

### 하지 않는 것

- 코드 수정, 커밋, 푸시, 머지, 태그, 브랜치 전환, stash, reset 을 하지 않는다.
- 로컬 체크아웃의 파일을 바꾸지 않는다. 일시적으로 바꿨다가 되돌리는 것도 안 된다. 실행이나 일부러 깨뜨려 보는
  시험이 필요하면 아래 임시 워크트리 안에서만 한다.
- PR 본문 수정, PR 닫기, 리뷰어 지정을 하지 않는다.
- 리뷰 대상 PR 말고 다른 PR 이나 이슈에 글을 쓰지 않는다.
- `.env.local`, 서명 키, 그 비밀번호의 내용을 출력하거나 PR 에 쓰지 않는다. 배포용 키로 서명하는 명령
  (`scripts/build.sh`, `NX4_APP_KEYS` 를 바꾸지 않은 `scripts/build-app.sh`)을 돌리지 않는다.
- 셸 명령을 `&&`·`||`·`;` 로 잇지 않는다. git 에 `-C` 를 쓰지 않는다.
- `cd` 에 기대지 않는다. 서브에이전트의 셸은 호출마다 시작 위치(로컬 체크아웃 루트)로 돌아오고 `cd` 는 다음 호출로
  이어지지 않는다. 그래서 `cd <워크트리>` 뒤의 명령은 체크아웃에서 돈다(2026-11-20 PR #5 리뷰에서 이 때문에 시험이
  체크아웃에서 돌고 체크아웃 파일이 바뀐 일이 있었다). 아래 "직접 확인" 처럼 git 은 체크아웃 루트에서, 워크트리 안의
  스크립트와 파일은 절대 경로로 다룬다.

### 순서

0. **시작 기록** — 다른 일을 하기 전에, 끝에서 비교할 체크아웃 상태를 적어 둔다(기록은 체크아웃 밖, 예: `mktemp -d` 로 만든
   임시 폴더의 파일).
   - `pwd` 가 지시문의 "로컬 체크아웃" 경로와 같은지 본다. 다르면 아무것도 하지 말고 그 사실만 알린다.
   - 체크아웃 루트에서 `git status --short`, `git rev-parse HEAD`, `git worktree list`
   - git 이 무시하는 빌드 결과: `shasum mod/app/NX4KOR.apk out/*.zip`. `git status` 에는 나오지 않지만
     `scripts/build-app.sh`·`scripts/build.sh` 가 체크아웃에서 돌면 여기가 바뀐다. 파일이 없으면 없다고 적는다.
   - 재리뷰 때도 매번 새로 적는다(그사이 메인 쪽이 체크아웃을 바꿨을 수 있다).
1. **맥락** — PR 본문과 변경 파일(`gh pr view <PR> --json title,body,files,baseRefName,headRefName,headRefOid`),
   전체 diff(`gh pr diff <PR>`), 관련 코드, `CLAUDE.md`·`docs/git-flow.md`·`docs/design.md` 를 읽는다.
2. **직접 확인** — 체크아웃 밖 임시 폴더에 워크트리를 만들어 실행한다. 아래에서 `<W>` 는 그 워크트리의 절대 경로다.
   - 체크아웃 루트(셸의 시작 위치)에서 `git fetch origin`
   - `mktemp -d` 로 임시 폴더를 만들고, 체크아웃 루트에서 `git worktree add --detach <임시 폴더>/review-pr-<PR> <head SHA>`.
     이 경로가 `<W>` 다.
   - 워크트리 안의 스크립트는 **절대 경로로** 부른다. 이 저장소의 PC 스크립트는 자기 위치(`dirname "$0"`)로
     저장소 루트를 찾으므로, 절대 경로로 부르면 `cd` 없이도 워크트리 기준으로 돈다. 워크트리에는 `.env.local` 이
     없으므로 체크아웃의 것을 `NX4_ENV_FILE` 로 가리킨다.
     - 늘: `NX4_ENV_FILE=<체크아웃>/.env.local sh <W>/tests/mod-test.sh` ("모두 통과"인지, 빌드·HMG-API 엔진 시험이
       돌았는지 "skip" 줄로 확인)
     - `app/` 를 바꿨으면: 임시 키 폴더(`mktemp -d`)로
       `NX4_ENV_FILE=<체크아웃>/.env.local NX4_APP_KEYS=<임시 키 폴더> sh <W>/scripts/build-app.sh`
   - PR 본문이나 답글이 주장하는 것(수치, "고쳤다", "실패를 잡는다")은 재현해 확인한다. 시험이 늘 통과하는
     시험이 아닌지, 일부러 깨뜨려 실패하는지도 본다. 깨뜨릴 때는 `<W>/…` 의 파일을 절대 경로로 고치고, 체크아웃의
     파일은 건드리지 않는다.
   - 끝나면 체크아웃 루트에서 `git worktree remove --force <W>` 로 지우고, 임시 폴더도 지운다. 지우는 것은 내가 만든
     `<W>` 하나뿐이다. `git worktree list` 에 보이는 다른 워크트리(다른 PR 의 리뷰어, 다른 세션)는 건드리지 않는다.
   - 돌려주기 전에 체크아웃 루트에서 0 의 기록과 비교한다: `git status --short`, `git rev-parse HEAD`,
     `git worktree list`(`<W>` 가 빠진 것 말고 같은지), 무시된 빌드 결과의 `shasum`. 다르면 고치려 하지 말고 무엇이
     어떻게 다른지 알림에 그대로 적는다.
3. **판단** — 다음을 본다.
   - 정확성: 버그, 경계 조건, 오류 처리, 회귀
   - 차에서 도는 스크립트(`mod/svc`, `mod/bin`, `mod/scripts`, `usb/troubleShooter`): 차의 셸은 mksh 다. bash 전용
     문법이 없는지, busybox 가 없을 때, root 권한·경로(`/data/...`)·부팅 단계 시점, 실패했을 때 차를 원래대로 두는지
   - HMG-API 모드: `mod/mod.json`(차종 제한 NX4·NX4HEV KOR 260902, `hmgapi` 최소 판, `conflicts`, 훅 지점),
     `patches.json`, 서비스 정의가 `docs/design.md` 와 맞는지
   - 상태 화면 앱(`app/`): Android API 19 에서 도는지(minSdk 19), 1920x720 화면, 앱과 root 가 주고받는 파일
     (`/data/local/tmp/nx4-kor-*.txt`, `reboot.req`)의 형식이 `mod/bin/status.sh`·`mod/svc/hotspot.sh` 와 맞는지
   - 사용자에게 보이는 한국어 문구: 정확하고, 차주가 무엇을 해야 하는지 알 수 있는지
   - 시험: 바뀐 동작을 `tests/mod-test.sh`·`tests/ReportTest.java` 가 덮는지, 실패해야 할 때 실패하는지
   - 문서: `README.md`, `docs/`, `NOTICE.md` 가 실제 동작과 맞는지
   - 저장소 규칙: `docs/git-flow.md`(base 브랜치, 판 번호는 `release/`·`hotfix/` 에서만), `CLAUDE.md`(코드에 PC 경로
     기본값을 두지 않고 `.env.local` 에서 읽음)
   - 보안·라이선스: 비밀값(키, `.env.local`)이 커밋되지 않았는지, 함께 넣는 GPL·AGPL 구성 요소의 고지
4. **CI** — `gh pr checks <PR>` 를 한 번 본다. 검사가 없으면 "CI 없음", 진행 중이면 그렇게 적는다. 기다리며 반복
   조회하지 않는다.

### 지적 쓰는 법

- 등급은 셋이다.
  - **반드시 고칠 것**: 합치면 잘못 동작하거나(차에서 포함) 저장소 규칙을 어기는 것
  - **권장**: 고치는 편이 확실히 나은 것
  - **사소함**: 문구, 사소한 정리, 지금 안 고쳐도 되는 것
- 번호는 PR 전체에서 이어서 붙인다. 첫 리뷰가 1–5 였으면 재리뷰의 새 지적은 6 부터다.
- 지적마다 위치(`파일:줄`), 이유, 실패 시나리오(어떤 입력이나 순서에서 무엇이 잘못되는지), 제안을 적는다.
- 직접 실행해 확인한 것과 코드를 읽고 추론한 것을 구분해 적는다(예: "코드를 따라가 확인했고 실행하지는 않았습니다").
  차에서만 확인할 수 있는 것은 그렇다고 적는다.
- 재리뷰에서는 지난 지적마다 해소 / 일부 / 미해소를 판정하고, 지난 지적 스레드에 확인 답글을 단다
  (`gh api repos/<R>/pulls/<PR>/comments/<comment id>/replies -f body=<답글>`). 범위 밖이라 남겨 둔 지난 지적은
  "그대로" 로 한 줄씩 적는다.

### 올리는 법

- 리뷰 본문·인라인 코멘트·답글 모두 **첫 줄을 `(자동 리뷰 — pr-<PR>-reviewer)` 로 시작**한다. PR 작성자와 같은
  계정으로 달리므로 이 머리말이 없으면 작성자의 반영 답글과 구분되지 않는다.
- PR 작성자와 같은 계정이라 승인(APPROVE)이나 변경 요청(REQUEST_CHANGES)은 쓸 수 없다. `event` 는 늘 `COMMENT` 다.

1. 리뷰 본문에는 다음 절을 둔다.
   - 요약: 무엇을 봤고 결론이 무엇인지(재리뷰면 지난 지적 해소 여부 포함)
   - 지적 사항: 반드시 고칠 것 / 권장 / 사소함 (없으면 "없습니다")
   - 지난 지적의 상태(재리뷰일 때)
   - 직접 실행한 확인: 명령, 결과 수치, 환경(빌드·엔진 시험을 돌렸는지 포함)
2. 줄을 짚을 수 있는 지적은 인라인 코멘트로도 단다. 인라인 코멘트는 PR diff 에 들어 있는 줄(`gh pr diff <PR>` 의
   hunk 안 줄)에만 단다. diff 밖 줄이 하나라도 있으면 리뷰 전체가 HTTP 422 로 거절된다. diff 밖 코드를 짚는 지적은
   리뷰 본문에만 적는다. 422 가 나면 문제 코멘트를 본문으로 옮겨 다시 올린다.
3. JSON 파일로 한 번에 올린다. 파일은 체크아웃 밖 임시 폴더에 쓰고, 올린 뒤 지운다.

   ```json
   {
     "commit_id": "<head SHA>",
     "event": "COMMENT",
     "body": "(자동 리뷰 — pr-<PR>-reviewer)\n\n<리뷰 본문>",
     "comments": [
       { "path": "<파일>", "line": <줄>, "side": "RIGHT", "body": "(자동 리뷰 — pr-<PR>-reviewer)\n\n<지적 번호·등급·내용>" }
     ]
   }
   ```

   `gh api repos/<R>/pulls/<PR>/reviews -X POST --input <json 파일>`

### 돌려줄 것

리뷰 내용 전문은 PR 에 있으므로 반복하지 않고 **짧은 알림만** 돌려준다.

- 리뷰 URL 또는 리뷰 id
- 등급별 지적 수 (예: 인라인 4건 — 반드시 1, 권장 2, 사소함 1)
- 재리뷰면 지난 지적 판정 수 (해소 / 일부 / 미해소)
- 직접 실행한 확인 한 줄(예: mod-test 102개 통과, 빌드·엔진 시험 포함)
- 체크아웃 비교 결과: 시작 기록과 같음, 또는 무엇이 다른지
- 이번에 본 head SHA
